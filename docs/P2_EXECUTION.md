# P2 第一批：执行资源与下游优先

延续P0/P1的任务制和TCP 1–65535完整性，本批改善已有执行器的资源估算和工作领取顺序。工具组合、进程硬上限、目标PPS与HTTP共享额度保持原有配置。

## 连接预算按实际路径计算

常驻Web helper的全局池默认最多2个进程，单入口串行采集；旧逻辑按HTTPx CLI的8线程预算计算每个HTTP任务，可能在仍有可用helper时停止领取。现在按实际入口数和执行路径预留：helper任务共享池容量，单入口占1份，旧批量入口不超过池的2份；CLI路径保留线程上限，原生路径按最多2个并发端点计。

尚未取得payload或尚未加载规则时保守预留，载入后按实际路径更新。端口、服务、HTTP、PoC的既有进程上限及总任务槽继续生效。连接数字是准入估算，不等于实际TCP连接数或硬网络并发保证。

## 服务积压时优先填充空闲服务槽

平台每5秒最多刷新一次共享快照，查询截止500毫秒。先按索引截取最老的1025个排队服务候选，仅统计前1024个，再过滤暂停/终结任务和不兼容profile。候选窗口截断时计数只是队列下界；更远的活跃任务可能暂未被看到，不以此阻止正常执行。

最老候选等待达到30秒，且采样端点不少于8个或估计累计工作达到90秒时，发出服务优先提示；退出采用10秒、4端点/45秒的低阈值。至少3份成本样本才估算累计工作量，估计不是完成倒计时。初次尚无成功快照或查询失败时不发优先提示，失败也缓存，避免反复查库。并发刷新期间可复用最多20秒前的成功快照，不延长该快照的原始时间；过龄即不提示，避免同步心跳时只有一个节点收到优先信息。

心跳携带`prefer_service`和`preference_ttl_seconds`，默认有效20秒。Agent仅在本机有空闲服务槽、Nmap可用、连接预算允许时优先尝试服务任务；没有兼容任务或目标额度不足时，继续原有领取顺序。单任务Agent保留原来的交替公平性，提示过期自动失效。

这是有界的下游优先策略，不是全局停止端口扫描。没有修改claim幂等、已取得的启动预留、区间清单、attempt、完成凭证或目标额度；也没有增加合批等待。它不承诺必然缩短每个任务的墙钟耗时。

## 各工具资源统计

Agent记录自己直接启动的Masscan、Nmap、HTTPx CLI、Web helper、fingers helper和Nuclei的进程数量与RSS。进程开始后注册，等待退出时移除；Linux结合PID和进程启动时间核对身份，避免把复用PID的新进程算到旧工具上。每个Agent拥有自己的fingers进程，在Agent退出时回收。

RSS为各直接受控进程的采样值，含共享页，不是完整进程树内存或物理内存去重值；极短进程可能不被采到。Linux无法读取的值和非Linux不支持的RSS省略，不填虚假的零。保留原Masscan字段，另外报告工具RSS合计、峰值、连接预算、上传积压及是否可继续接单。

Workers详情显示紧凑的工具表、连接预算和待上传量；离线节点标为最后记录。调度策略页显示是否优先领取端口指纹，详情放在提示框内。新指标在控制面按白名单、有限非负数和计数整数校验；发布顺序为控制面先更新，再更新空闲Agent。

## 后续开发顺序

本批之后继续扫描能力：逐跳核对范围的有限Web重定向、按候选产品选择的有限路径补采、成熟原始规则执行兼容性。补采仍共用请求预算、记录每次请求依据；不通过遍历全库扩大每个目标的请求量。截图、报告产品等外围能力维持独立范围，当前不混入执行与调度变更。
