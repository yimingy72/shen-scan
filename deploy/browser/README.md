# Browser runtime installation

The Agent release contains only these small scripts and a version policy. Chrome and its `.deb` are not bundled or downloaded during the release build. Run `sudo ./browser/install.sh ./browser` from an extracted release, or use `agent-bootstrap.sh`, which treats browser setup failure as a separate capability gap while continuing ordinary scanning.

Supported installer targets are Ubuntu 22.04+ and Debian 12+, Linux amd64 with systemd. The policy requires `google-chrome-stable >=155.0.8059.84-1` and the executable version `>=155.0.8059.84`. This is a minimum version, not an exact pin. An already sufficient/newer installation skips Chrome download/install; newer installed packages are never downgraded. The installer only uses the official stable apt repository, with normal apt signature/hash checks and a dedicated `signed-by=/usr/share/keyrings/shen-google-chrome.gpg` keyring. It verifies Google's published active primary key fingerprint before exporting only that key and its signed subkeys; it does not use apt-key or globally trust the downloaded key. When the installed browser already meets policy, an existing verified keyring is reused without downloading the key again. A browser install/upgrade refreshes the official key bundle so rotated signing subkeys are available, while keeping the same pinned primary fingerprint.

The installer records `/var/lib/shen-browser-install-status.json`. `browser_ready` is true only after version validation, the nonroot `shen-browser` user, wrapper installation and successful isolation service restart. `/var/lib/shen-browser-runtime.ready` is root-owned and created last; failures remove it. Runtime must probe the actual wrapper/isolation and launch result, rather than infer readiness from an installation attempt. Without readiness, the browser lane reports unavailable/incomplete; ordinary HTTP/Nmap/Fingers scanning can continue.

`shen-browser-network.service` runs at boot before the Agent. The Agent wants this service but does not require its success. Reinstallation rewrites the managed service/wrappers, reloads systemd and restarts the oneshot service to apply changes. Updating rules places a temporary deny guard before rebuilding the browser UID's dedicated IPv4/IPv6 chain. No chain update permits a direct browser network request. Failure retains denial and leaves readiness absent. IPv4 permits only loopback CDP replies on port 19222; IPv6 is denied. The root wrapper verifies readiness, the installed minimum version and exact firewall invariants before running Chrome as the dedicated nonroot user with its sandbox enabled.

The installer intentionally fails closed for missing signed-source access, an unexpected signing key, too-old repository candidates, unsupported platforms, missing systemd, or firewall failures. It does not provide an offline browser installation, automatic cloud provisioning, or install Chrome into the Agent archive. The bootstrap warning and status record identify the browser-specific failure.

Sources: [Google's Linux repository and active signing key](https://www.google.com/linuxrepositories/), [apt source signed-by](https://manpages.debian.org/bookworm/apt/sources.list.5.en.html), [apt package authentication](https://manpages.debian.org/bookworm/apt/apt-secure.8.en.html). Signing key URL: `https://dl.google.com/linux/linux_signing_key.pub`; expected primary fingerprint: `EB4C1BFD4F042F6DDDCCEC917721F63BD38B4796`. Key rotation requires an explicit reviewed policy/script update.
